# ANS Agent — аудит репозитория и путь к «arena-подобному» онлайн-агенту

Дата: 2026-09-13 · Базовый коммит: `b91df45` (origin/main) · Тесты: 64 passed / 0 failed

Цель владельца: свой агент в духе **arena.ai** (чат + Agent Mode + сравнение моделей),
с удобным веб-GUI, работающий **онлайн с VPS**, где сейчас поднят боевой VPN.

---

## 1. Резюме

Проект уже **на 60–70% пути** к цели по бэкенду и на ~40% по UX. Архитектура зрелая:
мульти-провайдерный роутер с ролями, политиками (cheap/balanced/quality), адаптивным
обучением по факту выполнения, circuit breaker'ом и fallback'ом; персистентные сессии и
задачи; песочница-workspace с git; approval-гейты; готовый одностраничный дашборд.

Главные разрывы до цели: (1) **безопасность онлайн-развёртывания** — агент исполняет
произвольный код, а его планируется выставить рядом с боевым VPN; (2) **UX-чат** — режим
CHAT сейчас прогоняет планировщик, а не даёт прямой ответ модели, нет стриминга и рендера
markdown/кода; (3) **отсутствие «arena»-экрана сравнения моделей** (пункт ROADMAP 19);
(4) эксплуатационные детали (воркеры задач живут в памяти, теряются при рестарте).

Вывод: **не переписывать**, а достроить. Ниже — что есть, разрывы, риски и дорожная карта.

## 2. Что уже есть (сильные стороны)

**Бэкенд (`core/`, `app.py`)**
- Роутер `ModelRouter`: ранжирование по ролям, `policy_rank` (cheap/balanced/quality),
  оценка стоимости, история успеха по ролям (`task_outcomes`), circuit breaker с
  half-open восстановлением, адаптивный fallback по классу ошибки (weekly_limit → не-anthropic).
- Провайдеры (`adapters.py`): Claude Code (локальный CLI), OpenAI/Gemini/OpenRouter
  (OpenAI-совместимые), Ollama (локальный, теперь надёжно детектируется, обход прокси).
- Оркестратор: режимы CHAT / AGENT / AUTOPILOT (parallel-граф) / BEST_OF_N; роли
  planner/researcher/architect/executor/tester/reviewer/fixer/judge.
- Персистентность: SQLite (сессии, события, задачи, статистика роутера, health).
- JobManager: очередь, отмена, таймауты, попытки; approval-гейты (блокирующие).
- API (~40 эндпоинтов): `/run`, `/route`, `/model-pool` (+ benchmark/discover/test/patch),
  `/jobs`, `/sessions`, `/workspace/*`, `/github/*`, `/learning`, `/circuit-breakers`,
  `/memory`, `/ws/{sid}` (WebSocket live-timeline), `/health`, `/diagnostics`, `/startup`.
- Деплой-заготовки: `deploy/Dockerfile`, `docker-compose.yml`, `nginx.conf`, скрипты
  install/backup/healthcheck.

**Фронтенд (`web/`)**
- Единый дашборд: задача → live-timeline (WS) → diff / файлы / редактор / git; пул моделей
  с приоритетами и тестами; adaptive learning; task graph; circuit breakers; approval-модалка;
  setup-диагностика; выбор profile/policy/budget/mode.

**Соответствие видению arena:** мульти-модель, роутинг, judge (BEST_OF_N), сравнение —
фундамент есть. ROADMAP уже содержит «19. Arena-style model comparison and judge».

## 3. Разрывы до цели (по областям)

### 3.1 UX / GUI
- **CHAT работает не как чат.** В `orchestrator.run` при `mode="chat"` вызывается
  `call("planner", ...)` и возвращается план как ответ. Для arena нужен прямой чат к
  выбранной модели (и/или к нескольким сразу) с историей диалога.
- **Нет стриминга токенов.** Ответы приходят целиком; live-timeline — это события агента,
  а не потоковый текст. Для «удобного GUI» нужен SSE/WS-стриминг ответа.
- **Нет рендера markdown/кода** в ответах (сейчас — плоский текст в timeline).
- **`web/app.js` продублирован 3 раза** (139 строк = троекратная копия всех функций).
  Работает (в JS побеждает последнее определение), но это технический долг.
- **Навигация не подключена.** Кнопки сайдбара (Agent/Projects/Sessions/Models) —
  чисто визуальные, без обработчиков; нет отдельных экранов.
- **Мелочи:** в селекторе mode «Autopilot» и «Autopilot Parallel» имеют одинаковый
  `value="autopilot"`; нет мобильной адаптации; тема одна (тёмная, инлайн-стили).
- **Нет «arena»-экрана:** параллельный запрос к нескольким моделям и side-by-side сравнение
  ответов/латентности/стоимости (BEST_OF_N есть в бэкенде, но не выведен в UI как сравнение).

### 3.2 Бэкенд
- **CHAT-режим** нужно развести с планировщиком (прямой вызов адаптера выбранной модели).
- **Стриминг** не реализован ни в адаптерах (Ollama `/api/chat` умеет `stream:true`;
  OpenAI-совместимые — SSE), ни в API.
- **Мульти-пользователь/сессии** отсутствуют: единый глобальный `AUTH_TOKEN`, одна воркспейс-папка.
- **Нет rate-limiting / квот** на публичных эндпоинтах.
- **История чата** как таковая не хранится отдельно от событий сессии.

### 3.3 Онлайн-деплой рядом с VPN (самое важное)
- Сервис проектировался как **локальный dev-агент**; в доках прямо: «Do not expose port
  directly to the Internet», «put TLS and an additional identity/access layer in front».
- Агент имеет инструменты **исполнения произвольного кода** (workspace exec, terminal, git).
  Публичный доступ = потенциальный RCE на той же машине, где боевой VPN и его данные.
- Аутентификация — **один общий Bearer-токен**; нет ролей, нет 2FA, нет аудита входов.

### 3.4 Надёжность / эксплуатация
- **Воркеры задач живут в памяти** (`JobManager` + потоки); при рестарте незавершённые
  задачи теряются (в доках это признано).
- SQLite ок для одного пользователя, но не для нагрузки/конкурентности.
- Нет системd-юнита/супервизора в репо (только Docker); нет структурированных логов/метрик.
- Рантайм-БД раньше коммитились; теперь закрыты `.gitignore` (уже поправлено).

## 4. Риски безопасности (блокеры до выхода онлайн)

Приоритет №1, потому что цель — выставить онлайн на VPS с боевым VPN.

1. **RCE-поверхность.** Executor исполняет код/команды в workspace. Любой, кто получит
   токен (или обойдёт слабую аутентификацию), исполняет команды на сервере VPN.
   → Изолировать: отдельный непривилегированный пользователь + контейнер + отдельная папка;
   в идеале — **отдельная машина/VM**, а не тот же хост, где VPN.
2. **Единый Bearer-токен** без ролей/ротации/аудита. → Добавить реальный слой аутентификации
   (reverse-proxy c basic/OAuth, или логин+сессии), TLS, и **IP-allowlist / доступ только
   через сам VPN** (не публиковать в открытый интернет).
3. **Секреты.** `.env` с ключами провайдеров и GitHub-токеном на хосте. → Только `.env`
   с правами 600, вне git (уже в `.gitignore`), бэкапы шифровать.
4. **Порт наружу.** По докам — только за nginx+TLS. → Не открывать порт приложения напрямую.
5. **CORS/WS.** Проверить, что WS-токен не утекает в логи (сейчас в query-строке).
6. **Соседство с VPN.** Компрометация агента = доступ к инфраструктуре VPN и его пользователям.
   → Сетевая сегментация (агент не должен иметь доступа к панели/БД VPN).

Рекомендация: **не публиковать в открытый интернет**. Держать агента доступным только
через сам VPN (доступ к панели только тем, кто подключён к VPN) или по IP-allowlist + TLS +
логин. Исполнение кода — в изолированном контейнере с не-root пользователем.

## 5. Дорожная карта (приоритезированная)

### P0 — обязательно до выхода онлайн
- [ ] Изоляция исполнения: Docker + непривилегированный пользователь + отдельная папка
      workspace; ограничить сеть контейнера (нет доступа к сети/панели VPN).
- [ ] Reverse-proxy (nginx) + TLS + слой аутентификации (basic/OAuth) поверх приложения.
- [ ] Доступ ограничить: только через VPN или IP-allowlist; порт приложения не публиковать.
- [ ] Проверить/зафиксировать хранение `.env` (600, вне git), ротация токена.
- [ ] Настоящий Ollama E2E на сервере + smoke `/health`, `/model-pool`.

### P1 — «arena»-UX (то, ради чего затевается)
- [ ] Полноценный **CHAT**: прямой вызов выбранной модели, история диалога, рендер markdown/кода.
- [ ] **Стриминг** ответа (SSE/WS) в адаптерах (Ollama/OpenAI-совместимые) и в UI.
- [ ] **Arena-экран**: один промпт → параллельно к N моделям → side-by-side (ответ/латентность/
      стоимость) + judge-выбор (BEST_OF_N уже есть в бэкенде — вывести в UI).
- [ ] Дедупликация и рефакторинг `web/app.js`; подключить навигацию сайдбара (экраны
      Chat / Agent / Arena / Models / Sessions).
- [ ] Починить мелочи UI (дубль value «autopilot», мобильная вёрстка).

### P2 — зрелость
- [ ] Мульти-пользователь (аккаунты, свои воркспейсы/сессии).
- [ ] Персистентность воркеров задач (переживать рестарт) или вынести в очередь.
- [ ] Структурные логи/метрики, systemd-юнит или healthcheck-рестарты.

## 6. Рекомендации по развёртыванию на вашем VPS

- **Отдельный хост/VM предпочтительнее.** Если только тот же VPS с VPN — запускать в Docker
  под отдельным пользователем, с ограниченной сетью, без доступа к панели/БД VPN.
- Схема: `nginx (TLS, auth, allowlist) → app (127.0.0.1:8000, в контейнере) → Ollama (127.0.0.1:11434)`.
- Доступ к UI — только через сам VPN или по IP-allowlist; не публиковать в открытый интернет.
- Ollama на CPU-VPS тянет `llama3.2`, но медленно; при слабом сервере взять модель полегче
  (`llama3.2:1b`, `qwen2.5:3b`).
- Бэкапы БД/workspace (`scripts/backup.sh`) — вне VPS, шифровать (могут содержать секреты).
